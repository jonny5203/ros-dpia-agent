## Goal

Replace the Docker Compose local runtime with a **kind (Kubernetes-in-Docker)** cluster so port conflicts like the `uvicorn`/`dpia-api` clash on 8000 can't recur (each pod has its own network namespace), and so compute resources are trackable via `kubectl`. The k8s stack must **behave identically to the current docker setup**: same services, same healthchecks, same `.env`-driven config, state persists across restarts, single command to bring up.

### Confirmed decisions
- **Replace compose** — kind becomes the primary/only local runtime. Remove `infra/docker-compose.yml` and the root `compose.yaml` include shim; remove compose-only Makefile targets; update README + IMPLEMENTATION_PLAN.md.
- **Dedicated cluster `dpia-ros`** with a single host port mapping `8081 → 80` (web app at http://localhost:8081). The existing `projectvault` cluster is untouched. All other services stay ClusterIP-internal (no host ports) — the original stack only truly needs `web:80` public.

### Secrets handling
The sensitive values live in `.env`. The Makefile generates a k8s Secret imperatively (stable name, gitignored):
```
kubectl create secret generic dpia-secrets --from-env-file=.env -n dpia-ros --dry-run=client -o yaml | kubectl apply -f -
```
Regenerated on every `make k8s-up`, so editing `.env` then re-running picks up changes (same UX as compose). api/worker load it via `envFrom`; the explicit `env:` overrides win for the k8s-specific URLs (k8s resolves duplicate keys in favor of explicit `env` entries).

### Compose → k8s mapping (the full picture)

| Compose | Kubernetes |
|---|---|
| service name DNS (`postgres`, `qdrant`, …) | Service with **same name** (bare-name DNS works in-namespace → `.env` unchanged) |
| named volumes (5) | PVCs (1 each, `ReadWriteOnce`, default kind StorageClass) |
| healthchecks | livenessProbe/readinessProbe (HTTP where curl existed, tcpSocket for qdrant, exec for pg/redis) |
| `depends_on: service_healthy` | readiness probes + `restartPolicy: Always` (pods self-heal as deps come up); no initContainers needed |
| `minio-init` sidecar | one-shot **Job** |
| `initdb/*.sql` | mounted into `/docker-entrypoint-initdb.d` (postgres image behavior identical) |
| `--import-realm` + realm JSON | same flag + ConfigMap-mounted realm |
| `x-backend` build anchor | single `dpia-ros-backend:dev` image, two Deployments, different `command` |
| `ports:` host mappings | only `web:80` exposed (NodePort 30080 → host 8081); rest ClusterIP |

### Images & loading
Built on host with docker, pushed into the kind node (standard kind workflow):
```
docker build -t dpia-ros-backend:dev ./backend
docker build -t dpia-ros-web:dev     ./frontend
kind load docker-image dpia-ros-backend:dev --name dpia-ros
kind load docker-image dpia-ros-web:dev     --name dpia-ros
```
Public images (postgres, qdrant, redis, minio, minio/mc, keycloak) are pulled by the kind node directly.

### Resource tracking (your stated motivation)
Each Deployment gets modest `resources.requests` (e.g. 100m/128Mi) + `limits` so `kubectl describe node` / `kubectl top` (if metrics-server added later) give meaningful visibility.

## Acceptance criteria (verification loop)

1. `make k8s-up` exits 0 with a fresh `dpia-ros` cluster; all pods reach `Running`, readiness gates green within ~3 min.
2. `curl -fsS http://localhost:8081/api/health` → 200 JSON (`status: ok|degraded`, `app: dpia-ros-backend`).
3. Browser at http://localhost:8081 loads the SPA.
4. MinIO bucket `kommune-docs` exists (minio-init Job `Completed`).
5. Keycloak realm `sandefjord` + client `dpia-bff` imported (check via Keycloak admin at the in-cluster endpoint).
6. `make k8s-down && make k8s-up` keeps data (PVCs persist).
7. `make k8s-nuke` removes the cluster cleanly; existing `projectvault` cluster is never touched.
8. No service binds host ports other than 8081 — `sudo lsof -i :8000` etc. stay clear.
