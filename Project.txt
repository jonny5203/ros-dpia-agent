Yes — **file upload + RAG is exactly what makes idea 6 strong**.

The Privacy / ROS / DPIA Assistant should **not** just be a generic chatbot that says “remember GDPR.” The impressive version is a **document-driven AI agent** where the user uploads project files, supplier documents, architecture notes, data-processing agreements, DPIA drafts, and municipal templates. Then the agent uses RAG to analyze the project against trusted guidance and internal routines.

The key point:

> **The AI should not “decide” whether Sandefjord is compliant. It should collect evidence, find gaps, generate draft risk documentation, and help humans complete ROS/DPIA faster.**

That is much closer to how a kommune would actually use it.

# How this should work

## 1. Two knowledge sources

You should design it with **two separate RAG areas**.

```text
A. Permanent knowledge base
   → Official guidance, templates, internal routines, checklists

B. Project upload workspace
   → Files uploaded for one specific project or procurement
```

This separation is important because the agent needs both:

```text
General rules and templates
+ actual project documentation
= useful DPIA / ROS analysis
```

---

# A. Permanent knowledge base

This is the material the AI always has access to.

For a Sandefjord-style demo, use:

| Source type         | Example content                                                                 |
| ------------------- | ------------------------------------------------------------------------------- |
| Legal/guidance      | GDPR Articles 5, 6, 9, 12–22, 30, 32, 35, 36                                    |
| Datatilsynet        | DPIA guidance, AI/privacy guidance, checklist                                   |
| Security guidance   | NSM grunnprinsipper, Digdir internkontroll/risk material                        |
| Municipal templates | ROS template, DPIA template, data processing agreement checklist                |
| Internal routines   | “How we assess new systems,” “how to classify data,” “how to handle deviations” |
| Procurement docs    | Supplier security questionnaire, cloud assessment checklist                     |
| AI governance       | AI usage policy, prompt logging policy, human review policy                     |

Datatilsynet describes a DPIA as a process that should describe personal-data processing, assess necessity and proportionality, and help manage risks to individuals’ rights and freedoms. They also emphasize that DPIA is part of accountability and documentation, not a replacement for checking the basic legal requirements first. ([Datatilsynet][1])

# B. Project upload workspace

This is where the user uploads files for a specific project.

Example:

```text
Project: AI assistant for HSO employees

Uploaded files:
- System description.pdf
- Supplier security questionnaire.docx
- Data processing agreement.pdf
- Architecture diagram.png
- Draft DPIA.docx
- ROS workshop notes.xlsx
- Access control matrix.xlsx
- Data flow description.md
```

The agent should then answer questions like:

```text
“Does this project require a DPIA?”

“Which parts of the DPIA are missing?”

“Extract all personal data categories from the uploaded documents.”

“Find risks related to health data, logging, access control, storage, and supplier processing.”

“Create a first draft of the ROS table.”

“Compare the supplier’s DPA with our checklist.”

“Which questions should we send back to the supplier?”
```

That is much more impressive than a normal chatbot.

# Important distinction

You should explain this clearly in your project:

| Method               |                                   What it means | Should you use it?                  |
| -------------------- | ----------------------------------------------: | ----------------------------------- |
| Normal prompt upload |       User uploads file and model reads it once | Good for demo, weak for real system |
| RAG                  |   Files are indexed and retrieved when relevant | **Yes, core approach**              |
| Fine-tuning          |         Training a model on municipal documents | Usually **no** for this use case    |
| Agent workflow       | AI uses tools to extract, compare, score, draft | **Yes, but controlled**             |

For this project, use **RAG + structured workflows**, not fine-tuning.

You can say:

> “We do not train the model on municipal documents. We store documents in a controlled project workspace, index them for retrieval, and retrieve only relevant chunks with citations when the user asks a question or runs an assessment.”

That sounds much safer for a municipality.

# The actual RAG setup

## Document ingestion pipeline

```text
Upload file
  ↓
Virus/file-type check
  ↓
Store original file in Blob Storage
  ↓
Extract text
  ↓
Split into chunks
  ↓
Create embeddings
  ↓
Store vectors + metadata
  ↓
Make chunks searchable per project
```

Each chunk should include metadata:

```json
{
  "chunkId": "doc-123-chunk-008",
  "projectId": "project-001",
  "documentName": "Supplier security questionnaire.pdf",
  "documentType": "supplier_security",
  "page": 4,
  "section": "Logging and monitoring",
  "uploadedBy": "project.manager@sandefjord.kommune.no",
  "classification": "internal",
  "createdAt": "2026-06-26T10:00:00Z"
}
```

The agent should cite sources like:

```text
According to the uploaded supplier questionnaire, prompts and responses are retained for 30 days [Supplier security questionnaire.pdf, p. 4].
```

This is critical. A privacy officer will not trust an AI answer without traceability.

# The agent should have 5 main tools

Do **not** start with 20 agents. Build one assistant with 5 controlled tools.

## 1. `AnalyzeUploadedDocuments`

Purpose:

```text
Extract project facts from uploaded files.
```

Output:

```text
Project summary
Data categories
Systems
Processors
Missing information
Possible sensitive data
```

---

## 2. `RunDpiaScreening`

Purpose:

```text
Check whether the project likely needs DPIA.
```

It should not say:

```text
“DPIA is legally required.”
```

It should say:

```text
“Based on the uploaded information, this project has indicators that normally require DPIA review: use of health data, new technology, systematic logging, and supplier processing. A privacy officer should confirm.”
```

This aligns better with Datatilsynet’s framing that DPIA is a structured process for assessing processing, proportionality, and risks. ([Datatilsynet][1])

---

## 3. `GenerateRosRegister`

Purpose:

```text
Create a risk table.
```

Example output:

| Risk                          | Cause                       |              Consequence | Likelihood | Impact | Suggested measure                                                |
| ----------------------------- | --------------------------- | -----------------------: | ---------: | -----: | ---------------------------------------------------------------- |
| Sensitive data uploaded to AI | Users upload case documents |   Confidentiality breach |     Medium |   High | Block fødselsnummer/health data, warn user, classify uploads     |
| Wrong DPIA advice             | AI hallucination            | Bad compliance decisions |     Medium | Medium | Require citations, human approval, “not legal advice” disclaimer |
| Excessive prompt logging      | Logs store personal data    |           Privacy breach |     Medium |   High | Minimize logs, retention policy, access restrictions             |

---

## 4. `CompareAgainstChecklist`

Purpose:

```text
Compare uploaded project with DPIA/ROS/supplier checklist.
```

Output:

```text
Complete:
- Purpose is described
- Supplier is identified

Missing:
- Retention period
- Data location
- Access control model
- Logging policy
- Subprocessor list
- Data deletion process
```

---

## 5. `DraftReport`

Purpose:

```text
Generate a draft DPIA/ROS document.
```

Export formats:

```text
Markdown first
DOCX later
PDF last
```

For speed, start with Markdown export. DOCX/PDF can be added after the core demo works.

# The most important feature: gap finding

The agent should not only answer questions. It should say:

```text
“I cannot complete this assessment because the uploaded files do not explain X, Y, and Z.”
```

For DPIA/ROS, missing information is often the real value.

Examples:

```text
Missing information:
- No retention period for prompts/responses
- No statement about model training
- No subprocessor list
- No access control description
- No deletion procedure
- No data location
- No incident response process
- No DPIA owner
- No human review responsibility
```

This is what makes the tool useful to privacy officers and project managers.

# Safety design

For a kommune, the assistant should have clear guardrails:

```text
The assistant may:
- summarize uploaded documents
- identify missing information
- draft DPIA/ROS text
- suggest questions for supplier
- suggest risk-reducing measures
- cite sources

The assistant may not:
- approve a DPIA
- declare legal compliance
- make decisions about citizens
- process real health data in a demo
- send documents externally without approval
- modify official records automatically
```

The EU AI Act uses a risk-based approach, and the Commission describes high-risk AI systems as subject to strict obligations before market placement; public-sector deployers of high-risk AI also have specific obligations around oversight, registration, and impact assessment depending on use case. ([Digital Strategy][2])

# Security architecture for upload + RAG

For the project, describe security like this:

```text
1. Files are stored per project.
2. Each project has its own access control.
3. Uploaded files are not used to train the model.
4. Retrieval is scoped to the current project and user permissions.
5. All answers include citations.
6. All analysis actions are audit logged.
7. Sensitive data detection runs on upload.
8. Retention policy controls when files and embeddings are deleted.
9. Human approval is required before exporting or using the report.
```

Important:

```text
Deleting a file must also delete:
- original file
- extracted text
- vector chunks
- analysis outputs
- generated draft reports, unless archived intentionally
```

This shows you understand that RAG creates derived data.

You are a municipal privacy and information-security assistant.
